# 答辩 / 演示要点（v32，2026-11-03）

> 这份是给"讲"用的，具体实现细节在 `QUAD_README.md`。
> 所有数字都来自实测或仿真，没有估算的地方都标了"约"。

## 一、系统能做什么（一句话版）

摄像头 + 千兆网 PC 视频 → DDR3 双页乒乓 → 1024×600 LCD 实时显示，
同时跑红绿灯识别、车道线检测（实线/虚线/变道）和决策提示，
结果直接叠加在画面上（红点 + 色块 + 英文）。

## 二、能力清单

| 模块 | 指标 | 备注 |
|---|---|---|
| 摄像头 | OV5640，1024×600，22fps | 场同步 22 次/秒（实测） |
| PC 视频 | 千兆 UDP，1024×600，24fps | 每帧 1200 包，信用流控 |
| 显示 | 1024×600 RGB LCD，3 种模式 | 按键 1 循环：PC 全屏 → 四宫格 → 摄像头全屏 |
| 图像算法 | 5 档：彩色/灰度/去噪/二值/YCbCr | PC 上位机经 UDP 命令切换 |
| 红绿灯 | 最多 4 个框 + 颜色分类 | STOP / GO / WAIT / LEFT 文字 |
| 车道线 | 左右两条，实线/虚线，偏移，变道 | 底部 240 行 ROI，单遍无行缓存 |
| 决策 | 9 种输出 | LOST / SOLID / LANE / WAIT / LEFT / RIGHT / STOP / GO / HOLD |
| 资源 | LUT 约 49%（v30 实测 11090/22560） | v31 新增约 1.6K LUT，预计 56% |

## 三、可以讲的五个技术点（面试/答辩最容易被问的）

**1. 为什么用"字流 + 标签"而不是"像素流 + 单独的行同步"**
标签（块号）和像素挤在同一条 17bit 通道里，从结构上排除错位；
如果 FIFO 因为任何原因丢字，写侧用 `ST_SKIP` 丢一个"不该出现在块首的字"
就能在下一个标签处自动重新对齐。单独用两个 FIFO 的话，一旦丢一个像素，
对应关系就永久错开，屏幕上是被斜着拉成条纹。

**2. 为什么翻页要等"这一页写完"**
早期版本块 0 一到就翻页，而块 0 那一拍同时被写进上一页 ——
屏幕最上面永远有半行旧画面。现在用 `pg_started/pg_last` 标记"本页从帧首开始
写、并且写到了帧末块"，翻页必须等这两个条件；残页不发布，宁可"停一帧"
也不让屏幕出现"半截新半截旧"。

**3. 跨时钟域为什么用翻转握手而不是异步 FIFO**
车道检测结果 45ms 才更新一次，用 FIFO 是杀鸡用牛刀，还要吃一块 DRM
（工程里只剩 31 块）。翻转握手 = 源域锁存数据后翻一位，目标域打两拍检测到
跳变再采。数据在采样时已经稳定了几十毫秒，物理上不可能采到半新半旧。

**4. 实线/虚线怎么判（这是本项目的算法核心）**
不能用"命中率"：透视条件下近处的线在图像里占的行多、远处占的少，
虚线在命中率上会被近处那一段拉得很高，看着像实线。
用**最长连续命中**：实线 ≈ 整个 ROI（240 行），虚线最长就是一个线段（40 行）。
这是两者唯一本质的区别。实测：实线 240、虚线 40，门限取 168 分得很开。

**5. 变道怎么判**
用**8 帧内车道中心的变化量**，不是偏移的绝对值 —— 绝对值对相机安装位置敏感
（装偏 5cm 基准就偏几十像素），变化量的符号直接就是变道方向。
另外只看到一条线时用上次学到的车道宽度补出另一条：变道过程中正被跨越的
那条线会跑出画面，而那恰恰是最需要判断的时刻。

**6. 算法怎么保证不是"拍脑袋调出来的"**
16 个仿真台，画面上每一类"烂输入"都有对应用例：只有一条线、低对比度（进隧道）、
路面亮斑（井盖）、单帧毛刺、急弯甩线；连"9 个决策词的英文字模"都单独抓点阵验过
（字母互相顶掉这种错，算法用例一个都不会失败）。而且每个用例都做**反向对照**——
故意把保护逻辑改坏，用例必须失败（例如把线型判据改成恒假，用例报 6 项不符）。
"跟丢后自动重捕"这条路径就是靠新用例跑出来的：原代码里放宽窗口比参数注释写的
晚一帧，改完重捕从第 4 帧提前到第 3 帧。**这种 bug 看代码看不出来，只有把路径跑起来才看得见。**

## 四、现场演示流程（3 分钟）

1. **上电** → PC 全屏，视频在放（说明传输链路通了）
2. **按键 1 切四宫格** → 左上摄像头、右上/下 PC 三格（说明双路合成）
3. 指着左上格说：**红点是车道线跟踪点，三个色块是"左线型/右线型/决策"**
4. **按键 2 关掉图层** → 画面变干净（说明这是可开关的诊断图层，不影响主画面）
5. **按键 2 开回来**，拿一张纸/一个盒子放在摄像头前当"实线"挡住 → 色块变绿
6. **PC 端切二值化/灰度** → 整屏一次性变，没有彩色残留（说明写通路算法链）
7. **拔网线** → 画面定格在最后一帧，2 秒后自动退到四宫格（说明断流兜底）

## 五、可能被问到的问题

**Q：为什么不用 OpenCV 在 PC 上做？**
A：赛题要求板上实时处理。车道线检测放在 FPGA 里，从像素进到结果出延迟
不到一帧（45ms），而且摄像头画面不需要经过 PC 绕一圈。

**Q：为什么不做车辆检测？**
A：板上做车辆检测（车底阴影/竖直边缘对称）需要 2~3 块 DRAM 行缓存，
而且检出率在白天高速场景只有 60~80%，真正的成本在调参 ——
每次改阈值要一次完整的综合布线（20~40 分钟）。在交付周期内它是负收益，
所以把时间放在能稳定做对的车道线和决策上。这是主动取舍，不是做不出来。

**Q：22fps 够用吗？**
A：显示刷新 22fps 是摄像头场同步决定的（摄像头本身就是 22fps）。
PC 通路 24fps，两者用帧闸门对齐，不会出现"一页混两帧"。

**Q：怎么保证不会花屏/撕裂？**
A：三道保险：① 标签自愈（错位最多丢一块）；② 翻页完整性检查（残页不发布）；
③ 页对齐（新页只认帧首块）。每一条都有对应的仿真用例，并且做过反向对照
（把保护关掉，同一个用例必须失败）。

**Q：资源还剩多少？**
A：v30 综合结果 LUT 49%、FF 25%、DRM 49%（29/60）。v31 加了车道线和 OSD，
估算 LUT 到 56%、DRM 一块没多用（检测不用行缓存）。

## 六、如实说明的边界（被问到就直说，别硬撑）

- **没做闭环控制**：只输出"提示"，不控制方向盘/油门。赛题要的是辅助驾驶提示的话没问题
- **夜间/逆光没优化**：阈值是自适应中点，进出隧道会有一帧延迟
- **急弯会跟丢**：跟踪窗 ±64，跟丢后连丢 2 帧，第 3 帧（≈60ms）自动放宽到 ±192
  并用种子位置重捕；急弯太急的话会反复丢-捕，这段时间输出 `LOST` 而不是乱报
- **四宫格下没有红绿灯识别**：现成的 traffic_light 只扫 PC 那半屏
- **v31 还没上板**：算法和 OSD 都在仿真里验证过，真实光照下阈值要重调
