# 摄像头帧率分析 / 提速方案 / 车辆行驶状态识别可行性

日期：2026-11-03　　对应固件：v41（版本标记 3'b101）
实测手段：板子 UDP 遥测（1234 端口）在线抓取，无需示波器

---

## 一、22 fps 是怎么来的：实测 + 公式，两边对得上

### 1.1 板上实测（遥测原始数据）

板子每消费一批 PC 像素就回一个 39 字节广播包，其中 `'T''L'` 块里是：

| 字段 | 位置 | 含义 |
|---|---|---|
| q_pc_px | 22~25 | PC 已落盘像素（累计） |
| q_cam_px | 26~29 | **摄像头已落盘像素（累计）** |
| pc_level | 30~31 | PC FIFO 水位 |
| cam_rd_level | 32~33 | 摄像头 FIFO 水位 |
| 低字节 | 37 | `[7:5]`算法档 `[4:3]`显示模式 `[2:0]`版本 |

抓 8 组，用「Δcam_px / Δt ÷ 614400」反推帧率（当前处于 mode=2 摄像头全屏）：

```
cam_rate=13671319 px/s   fps=22.25   cam_fifo= 512/4096
cam_rate=13057486 px/s   fps=21.25   cam_fifo= 383/4096
cam_rate=13817347 px/s   fps=22.49   cam_fifo= 373/4096
cam_rate=13001692 px/s   fps=21.16   cam_fifo= 391/4096
cam_rate=13896610 px/s   fps=22.62   cam_fifo= 367/4096
cam_rate=12920198 px/s   fps=21.03   cam_fifo= 429/4096
cam_rate=13760270 px/s   fps=22.40   cam_fifo= 331/4096
cam_rate=12958304 px/s   fps=21.09   cam_fifo= 261/4096
```

**均值 21.8 fps**，与屏上 `FPS 22` 一致。抖动 ±1.6 fps 是遥测采样（每 0.25 s 一次、125 MHz→50 MHz 同步）带来的，不是摄像头真抖。

### 1.2 公式反推 PCLK

OV5640 帧率公式：

```
fps = PCLK / (HTS × VTS)
```

代入实测 21.8：

```
PCLK = 21.8 × 2200 × 1000 = 47.96 MHz ≈ 48 MHz
```

和 `i2c_ov5640_rgb565_cfg.v` 第 204 行的注释**逐字吻合**：

```verilog
//系统时钟分频 Bit[7:4]:系统时钟分频 input clock =24Mhz, PCLK = 48Mhz
8'd205: i2c_data <= {16'h3035,8'h11};
8'd206: i2c_data <= {16'h3036,8'h3c}; //PLL倍频
```

### 1.3 三个数字一起看，才知道余量在哪

| 参数 | 寄存器 | 值 | 拆开看 |
|---|---|---|---|
| PCLK | 0x3035/0x3036 | 48 MHz | 24 MHz 晶振 × 60 倍频 ÷ 30 |
| HTS | 0x380C/0x380D | 2200 | **2048 数据 + 152 消隐** |
| VTS | 0x380E/0x380F | 1000 | **600 有效行 + 400 消隐** |

关键点：DVP 是 **8 bit 模式**（`cmos_capture_data.v` 里 `byte_flag` 每 2 个 PCLK 才拼出一个 RGB565 像素），所以 1024 像素一行要占 2048 个 PCLK。

**HTS 里只剩 152 个 PCLK 的消隐，已经挤不出空间了。**
**VTS 里躺着 400 行消隐 —— 帧率余量全在这儿。**

这 400 行不是浪费：VTS 决定自动曝光的最大行数，暗光下曝光会一直顶到 VTS。所以砍它就是拿暗光画质换帧率。

## 二、FPGA 侧完全不是瓶颈（有实测证据）

这是最容易误判的地方：22 fps 看着像"逻辑跑不动"，其实跟逻辑一点关系没有。

| 环节 | 能力 | 实际用量 | 结论 |
|---|---|---|---|
| cam FIFO（4096 深） | — | **261~512（6~12%）** | 空得很 |
| 块搬运（1 像素/拍 @50 MHz） | 50 M px/s | 13.5 M px/s | **27%** |
| DDR3（800 MT/s × 2 B） | 1600 MB/s | 读 72 + 写 27 = 99 MB/s | **6%** |
| LCD 读（50 MHz，de 占空比 76%） | 38 M px/s | 36 M px/s | 95%，但这是屏幕刷新本身 |

`cam_fifo` 长期只有 6~12% 水位，说明**搬走的速度是摄像头给的速度的 3.7 倍**。摄像头翻倍到 40 fps 时水位会升到 ~25%，仍然安全。

唯一接近满载的是 LCD 读通路（屏幕 58.6 Hz 刷新必须吃掉 36 M px/s），但它和摄像头帧率无关 —— 屏是固定 58.6 Hz 刷的。

## 三、提速方案（按风险从低到高）

### 方案 A：只降 VTS（推荐先做这一个）

**改一处**：`rtl/eth_ddr3_lcd.v` 第 81 行

```verilog
localparam [12:0] CAM_TOTAL_V = 13'd1000;   // ← 改成 700
```

寄存器 0x380E/0x380F 是运行时由这个 localparam 算出来写进去的，改它等于改 OV5640 的行周期。

| VTS | 预期 fps | 相对现在 | 最大曝光时间 | 暗光影响 |
|---|---|---|---|---|
| 1000（现状） | 21.8 | — | 45.8 ms | 无 |
| 800 | 27.3 | +25% | 36.6 ms | 基本无感 |
| **700** | **31.2** | **+43%** | 32.0 ms | 暗处噪点略增 |
| 660 | 33.1 | +52% | 30.2 ms | 同上 |
| 640 | 34.1 | +56% | 29.3 ms | 已接近下限（600+40） |

- 风险：**极低**。不动 PCLK、不动 DVP 时序、不动 FPGA 任何逻辑，摄像头输出格式完全不变，`cam_line_pick` / FIFO / 搬运一条线都不用改。
- 唯一要盯的是开机初始化：VTS 改小后 OV5640 的 AEC 稳定得更快，没有副作用。
- 验证：烧进去看屏上 `FPS`，应该显示 31 左右；再抓遥测确认 `cam_px` 率 ≈ 19.2 M px/s。

**建议取 700**：+43% 的收益，曝光余量还留得住（32 ms 对室内/白天足够，夜间会靠增益补）。

### 方案 B：降 VTS + 提 PCLK（要动摄像头时钟）

**改两处**：

```verilog
// i2c_ov5640_rgb565_cfg.v 第 323 行
8'd206: i2c_data <= {16'h3036,8'h3c};   // ← 0x3c(60) 改成 0x48(72)

// eth_ddr3_lcd.v 第 81 行
localparam [12:0] CAM_TOTAL_V = 13'd700;
```

PCLK 48 → 57.6 MHz，配合 VTS=700 得 **37.4 fps**；VTS=640 得 **40.9 fps**。

代价与风险：

1. **PCLK 超标定约束**。`prj/eth_ddr_lcd.fdc` 第 4 行写死了 `-period {20.000}`（=50 MHz），实际跑 48 MHz 还剩 2 ns 余量；提到 57.6 MHz 就超出约束 2.6 ns。必须同步把约束改成 17.36，然后重新看 `cam_pclk` 域的时序 —— 而当前全设计 WNS 已经是 **−2523 ps**（本来就是负的），再压 2.6 ns 风险不小。
2. **DVP 排线信号质量**。8 bit 并行 + PCLK，57.6 MHz 下边沿更陡，长排线容易误码（表现为偶发花屏/条纹）。
3. PLL VCO 从 360 MHz 升到 432 MHz，OV5640 允许，但 ISP 内部时钟一起变，白平衡/曝光的收敛速度会变。

结论：**能做，但收益（31→37）不如代价大**。建议先做 A，看 31 fps 够不够，不够再上 B。

### 方案 C：为什么不能靠降 HTS

HTS 已经是 2200 = 2048（数据期）+ 152（消隐）。数据期是 8 bit DVP 的物理下限，**除非把摄像头改成 16 bit DVP 接线**（硬件改板，不现实）。所以 HTS 这条路是死的。

### 方案 D：降分辨率（不推荐）

1024×600 降到 800×480，像素少 37%，但那要重做 `cam_line_pick` 的块映射、DDR 布局、四宫格排版 —— 等于重做显示链路，和"不影响现有功能"直接冲突。

## 四、重要前提：不是所有显示模式都能吃到这个提升

| 模式 | 屏幕刷新由谁决定 | 提高摄像头帧率的实际效果 |
|---|---|---|
| **摄像头全屏**（mode 2） | **摄像头帧率本身**（一帧写完就翻页） | **直接有效**：屏从 22 Hz 变 31 Hz，肉眼明显更顺 |
| 四宫格（mode 1） | PC 帧（`pg_last`，约 24 fps） | 只让左上那格更新更勤，整屏仍 24 Hz |
| PC 全屏（mode 0） | PC 帧 | 完全无关 |

也就是说：**这个改动在摄像头全屏档最值钱**，四宫格里别期待"整屏变流畅"。

如果目标是四宫格也变顺，那要提的是 PC 端发送帧率（`BOARD_FPS_DEFAULT = 24.0`，受 `GAP_MIN_US = 40 µs` 限制，天花板 27.8 fps），以及翻页策略 —— 那是另一条线。

## 五、车辆行驶状态识别：可行性评价

### 5.1 先说结论

**可行，但只能做到"定性"，且分两档成本。**

- 能做到：直行 / 左转 / 右转 / 停止 / 前进中（相对快慢），以及"车道内左偏/右偏"
- 做不到：绝对车速（km/h）、加速度的物理值
- 原因：没有 IMU、没有轮速、没有 GPS，摄像头也没标定过内参外参。所有量都是"像素/帧"，没有物理量纲。

### 5.2 现成可用的量（不用新写检测器）

`lane_detect` 每帧结算一次，已经在往外送这些东西：

| 信号 | 位宽 | 含义 | 对行驶状态的用途 |
|---|---|---|---|
| `offv` | 11 补码 | 车道中心 − 512 | 帧间差分 → 横向速度、车道内漂移 |
| `anch` | 88 | 4 行(420/480/540/599) × 左右线的 x | 拟合车道线倾角/曲率、透视扩张率 |
| `lstate` | 3 | 0居中 1偏左 2偏右 3变道 7无效 | 已有的粗分类，可直接复用 |
| `cdir` | 2 | 1右 2左 | 变道方向 |
| `ltyp/rtyp` | 2+2 | 实线/虚线/判不出 | 辅助可信度判断 |

**关键**：这些量是"每帧一次"的慢变量（`tick` 脉冲驱动），不在像素流水线上。加逻辑不会拖累 50 MHz 的像素路径 —— 这是这次能做的根本原因。

### 5.3 三个可选算法，成本差一个数量级

#### 档 1：车道几何法（推荐先做）

只用现成的 `offv` / `anch`，存上一帧的值做差分：

```
横向速度   vx = offv(t) - offv(t-1)              # 像素/帧
偏航角     yaw ∝ (anch_L@420 - anch_L@599)       # 线的斜率，车头相对车道方向
曲率       κ  ∝ 三点拟合的二阶差
前进/停止  用车道宽度 D(t) = anch_R@599 - anch_L@599
           D 变大 → 前进（透视扩张）；D 不变 → 静止；D 变小 → 倒车
```

输出 5 态：`直行 / 左转 / 右转 / 静止 / 无法判断`，再叠一个"左偏/右偏"标记。

- 成本估算：约 **80~140 LUT，0 块 BRAM，0 个 DSP**（几个 11 位减法器 + 比较器 + 5 帧去抖计数器）
- 全部挂在 `tick` 路径上，不碰像素流水线
- 已知缺陷：
  - 车道线丢失（`lstate==7`）时无输出 —— 必须显式报"无法判断"，不能硬猜
  - 坡道、弯道会让 `D(t)` 变化，和"前进"混在一起，需要靠曲率交叉验证
  - 车身抖动（过坎）会污染 `vx`，要加中值/去抖
  - 精度：`vx` 1 像素/帧 ≈ 每秒 22 像素的横向位移，标定前只是个相对量

#### 档 2：块匹配光流（如果有余力）

在 ROI 底部取 1~2 个 16×16 块，在下一帧的 ±8 范围内做 SAD 搜索，得到全局位移矢量 (dx, dy)。

- 运算量：17×17 位置 × 256 像素 = 74k 次/块/帧，22 fps → 1.6 M 次/s，50 MHz 下约 3% 占用，**算力上完全够**
- 成本估算：**600~900 LUT + 1 块 BRAM（存参考块 16×16×8b）+ 可能 1~2 个 DSP**（APM 现在只用了 4/40，够）
- 收益：`dy` 直接给"前进/停止/倒车"，`dx` 给横向漂移，比档 1 稳得多
- **风险**：当前 WNS = **−2523 ps 已经是违例状态**（所有版本都一样，板子能跑但临界）。加 600~900 个 LUT 且涉及 256 路并行的比较树，很可能把时序推得更差。要做的话建议把 SAD 阵列改成"每拍 1 个像素、256 拍出一个位置"的串行结构，用 74k 拍/帧 = 1.5 ms/帧，时间上完全来得及，资源只剩一个加法树。

#### 档 3：帧差法（最省，但最粗）

把 ROI 缩到 64×48 灰度存进 BRAM，逐像素和上一帧比，统计"整体朝哪个方向平移"。

- 成本：3 块 DRM（现在 29/60，够）+ 约 300 LUT
- 只能给"画面在动/没动"，方向要靠直方图投票，精度最差
- 不推荐，除非只要一个"车辆是否在动"的灯

### 5.4 硬性限制（必须提前知道）

1. **输入是 PC 视频，不是摄像头**。v34 起车道识别跑在 PC 像素上（`full_scr` 才有效），所以"行驶状态"只对 PC 那一路视频成立。摄像头全屏档没有车道识别。
2. **没有标定就没有物理量纲**。想输出 km/h，必须先在固定机位测一次"车道宽 1 像素 ≈ 多少米"，写死一个标定常数；换个机位就得重标。
3. **时序余量已经很薄**。WNS −2523 ps、LUT 55%、DRM 49%、PLL 3/4 —— 再做大的图像处理要谨慎，尤其是任何进 `clk_50m` 的组合逻辑。
4. **演示可信度**。档 1 的输出在直线匀速行驶时几乎是常量（"直行"），只有转弯/停车才有变化，演示时不容易看出效果。建议同时把 `vx`、`D(t)` 的原始值显示在 OSD 上，让人看到"数字在动"。

### 5.5 建议的实施顺序

```
第 1 步  档 1 几何法，只输出 5 态 + 把 vx/D 原始值放 OSD 角上
         验证：拿一段已知"直行→左转→停"的素材，看状态是否跟着变
第 2 步  若抖得厉害，加 5 帧中值 + 车道线有效位门控
第 3 步  若还不够，再上档 2 的串行 SAD 光流（先只做 dy，即前进/停止）
```

## 六、附：遥测怎么自己抓

```python
import socket, struct, time
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(("", 1234)); s.setblocking(False)
# 发几个合法视频包头触发回包（也可以直接跑 video_sender.py）
tx = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); tx.connect(("192.168.1.10", 8080))
tx.send(struct.pack(">HHHH", 0xA55A, 1, 0, 8) + b"\x00"*16)

d = s.recvfrom(2048)[0]
i = d.find(b"TL"); f = d[i+2:]
cam_px = struct.unpack(">I", f[4:8])[0]     # 摄像头累计落盘像素
low    = f[15]                               # [4:3] 显示模式  [2:0] 版本
```

注意：包的第一个字节（`'C'`）被 `udp_tx` 流水线吃掉了，所以偏移要靠 `find(b"TL")` 对齐，不能按文档从头数。
